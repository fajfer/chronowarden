# Built-in webhook alerting

- **Status:** approved
- **Date:** 2026-10-12
- **Issue:** #99

## Goal

A solo admin gets notified in a chat tool without running Alertmanager: Chronowarden sends Alertmanager-compatible
webhooks to the effective owner of a secret (through the owner's webhook routes) when it rotates, waits too long for
confirmation, is about to expire or expires, and to configured default routes for vault-health and compliance events
and for secrets without an owner. Deliveries are retried, logged, and can be signed (Standard Webhooks).

## Non-goals

- Email, chat-specific formats (Slack blocks, Teams cards): receivers that need them sit behind a small adapter.
- Silences, grouping and inhibition rules (Alertmanager's job for those who run it).
- Authentication for the endpoints that manage routes (0.9); the SSRF risk stays accepted and documented (ADR-022).

## Decisions (maintainer, 2026-10-12)

- Events without an owner (vault health, compliance, unowned secrets) go to **`alerting.default_routes`** in config.
- A still-firing alert is **re-sent every `alerting.repeat_interval`** (default `1d`) and sent once more as
  **resolved** when it ends (Alertmanager-like).
- Each route's **signing secret is generated by Chronowarden**, shown once, and stored in SQLite (never returned).
- **Settings → Owners** manages routes: add, delete, turn signing on or off, send a real test webhook.

## Design

- **Alerts** have a name, labels and a fingerprint (SHA-256 of the name and labels), like Alertmanager:
  - *state alerts* fire while a condition holds and resolve when it ends: `SecretExpiringSoon` (status warning),
    `SecretExpired`, `SecretRotationUnconfirmed` (confirmation overdue), `VaultUnreachable` (offline or auth
    failure; resolves when the vault is back);
  - *event alerts* fire once: `SecretRotated` (a new version seen by sync), `SecretRotationConfirmed`,
    `CompliancePeriodEnded`, `ComplianceSnapshotCreated`.
- **Evaluation** runs after every sync (secret alerts, from the enriched secrets), on vault connection changes
  (health) and on the scheduler tick (periods ended); event alerts are raised where the event happens (sync's
  `secret.version` observation, `POST .../confirmations`, `POST /compliance/snapshots`).
- **State** lives in a new table (migration 10) keyed by fingerprint: status, starts/ends, last sent. A firing alert
  is sent when it starts, then every `repeat_interval`, and once as resolved.
- **Recipients**: a secret alert goes to every webhook route of the secret's effective owners; with no owner, and for
  instance alerts, to `alerting.default_routes` (URL or `url_env`/`url_file`, optional `signing_secret_env`).
- **Payload**: Alertmanager webhook JSON (`version: "4"`, `status`, `receiver`, `alerts[]` with `labels`,
  `annotations`, `startsAt`, `endsAt`, `fingerprint`, `generatorURL`), metadata only: paths, owners, systems, dates.
- **Delivery**: a queue table (migration 10) and an in-process worker: POST with a 10 s timeout, no redirects,
  retries with backoff (1 min, 5 min, 30 min, 2 h; at most `alerting.max_attempts`, default 5); the log keeps status
  code and error per attempt. `NOTIFICATIONS_SENT_TOTAL{router_type="webhook", status}` counts outcomes.
- **Signing** (Standard Webhooks): headers `webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64
  HMAC-SHA256 of "id.timestamp.body">`; secrets are `whsec_<base64>`.
- **Config** `alerting`: `enabled` (default true; nothing is sent without routes), `events` (default all),
  `repeat_interval`, `max_attempts`, `default_routes`, `external_url` (for `generatorURL`).
- **API**: `GET /alerts` (firing alerts), `GET /webhooks/deliveries` (log, newest first), `POST/DELETE
  /owners/{id}/routes/{route_id}/signing` (secret shown once), `POST /owners/{id}/test-route/{route_id}` sends a
  real test webhook and reports the outcome. Route signing changes are audit events; deliveries are not.
- The one-shot command evaluates and enqueues like the server, then delivers what is due before it exits.
